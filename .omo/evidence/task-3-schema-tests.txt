## Staging Schema Tests (dbt/models/staging/schema.yml)

### Model: stg_funding_events

**Column-level tests:**

| Column | Tests | Rationale |
|--------|-------|-----------|
| venue | not_null | Every event must have a source venue |
| symbol | not_null | Every event must have a trading pair |
| asset_class | not_null, accepted_values: ['crypto', 'equity'] | Discriminator required; only two valid classes |
| interval_start | not_null | Every event must have a timestamp |
| funding_rate_annualized_pct | not_null, accepted_range: [-500, 500] | Normalized rate required; negatives allowed (shorts pay longs), extreme range for market stress |

**Key design decisions:**
- `accepted_range` allows negative values (-500 to 500) — negative funding is signal, not error
- `asset_class` uses `accepted_values` to enforce crypto/equity discriminator
- `interval_hours` has no not_null test — Hyperliquid provides this, but it's derived for others
- `premium_bps` has no test — NULL when index_price unavailable (Hyperliquid)

### Marts Layer
- ✅ not_null on all dimension columns (venue, symbol, asset_class, date/hour)
- ✅ accepted_values on asset_class across all 3 mart tables
- ✅ unique compound keys on all 3 mart tables:
  - mart_hourly_funding: (venue, symbol, hour_start)
  - mart_daily_funding: (venue, symbol, date)
  - mart_venue_comparison: (date, symbol)

### Design Principles Applied
1. **No filtering of negative rates** — accepted_range explicitly allows -500 to 500
2. **asset_class discriminator present** — crypto vs equity classification enforced
3. **Compound key uniqueness** — prevents duplicate aggregations in marts
4. **Venue-agnostic tests** — no venue-specific logic in shared mart models
